## D-004 The OpenDeck client runs on the device
- **Observed:** the stock firmware makes the SK-18 a USB CDC-ACM peripheral controlled by a PC application; it has no network client.
- **Decision (user, 2026-11-07):** the final image runs a client on the SK-18 itself. It connects over Wi-Fi to OpenDeck or to the user's `controldeck-rs` app, shows images on the keys and sends commands, like a Stream Deck.
- **Consequences:** Wi-Fi (RTL8188GU), the display pipeline (including per-key images) and touch/key input are required for the final image, not optional. The client protocol is specified by OpenDeck / `controldeck-rs`, not by the stock serial protocol; the stock protocol is only useful for understanding the hardware.
- **Open:** the exact OpenDeck transport and the `controldeck-rs` interface (to be provided by the user).

## D-006 How the on-device client reaches `controldeck-rs`
- **Observed:** `controldeck-rs` (`C:\Users\mholmert\Workspace\control-deck-rs`, also on the DietPi machine) is a gateway: `DeviceProvider` drivers (currently Elgato, over USB HID) feed `gatewayd`, which serves the OpenDeck plugin through `/ws/client` (JSON over WebSocket: `hello`, `claim`, `set_outputs` with `image`/`fill`/`clear`/`brightness`, and `input` events; token auth; one client slot). - **Inferred:** the SK-18 needs a device-side connection to the gateway, i.e. the gateway treats it as a network-attached deck. `/ws/client` does not fit (it is the consumer side).
- **Options:** (A) add a new "remote device" endpoint and `DeviceProvider` to `controldeck-rs` that the SK-18 client connects to; (B) as an interim step, write a `deck-sk18` driver that uses the stock firmware's USB serial protocol so the gateway side can be developed and tested before the Linux port is finished.
- **Open:** user to choose between A, B or both.

## D-020 Black screen: the panel was never initialised (2026-11-08)
- **Observed (register diff, stock vs mainline, `work/regs_diff.py`):** CCU display clocks, TCON top, D-PHY and the mixer chain are the same on both systems, so clocks, routing and the video path are not the problem. Two real differences: (1) the DSI **command buffer** (+0x300..) of the working stock system holds DCS packets and the mainline one is empty; (2) PE5 (`PE_DAT` bit 5) is **low** on stock and **high** on mainline.
- **Decoded:** the stock buffer starts `05 29 00 1c`, a DCS short write of **0x29 (display on)**; behind it is a long write `B2 00 80 64 0c 06 2f 00 00 00 00 c0 18` whose CRC (`5f bc`) overwrote the tail of an earlier **E0 (gamma)** write. The stock panel therefore receives a full HX8394 initialisation. The previous finding "the stock kernel sends no panel commands" stays true (its `default_lcd` init is empty); the commands come from the stock **U-Boot**, which initialises the panel (that is also the boot animation) and the kernel then takes over without touching it.
- **Found in the U-Boot image:** `rawboot.bin` offset `0x010941b4` holds the panel tables (next to the strings `lcd_compatible_index.txt` and `/soc/lcd0_0`): three variants (HX8394 `B9 FF 83 94`, HX8399 `B9 FF 83 99`, and an Ilitek-style set). The HX8394 table is the one whose last long write matches the register leftover, and it equals mainline's `waveshare,5.0-dsi-touch-a` sequence (same panel family, same 70 MHz pixel clock) up to the gamma table; it then differs slightly and ends with a 12-byte `B2`.
- **PE5:** configured as an output and driven low on the working stock system; the vendor DTB gives it flag 1. So PE5 is an **active-low panel power enable**. The earlier "held low for 45 s" test could not show anything because the panel had no initialisation yet.
- **Changed (not yet run on the board):** `patches/linux/0001` is replaced: instead of a `panel-simple` entry (no commands) the SK-18 is now an entry in `panel-himax-hx8394.c` with the exact stock byte sequence, the stock timing, then sleep-out, 120 ms, display-on (the driver's existing flow; the sun6i DSI host calls `drm_panel_enable()` before it starts the high-speed clock, so the commands go out in low-power mode, the same order as stock). DTS: a `regulator-fixed` on PE5 (active low) feeds `vcc-supply` and `iovcc-supply`; the `enable-gpios`/`power-supply` guesses are gone. Kernel fragment: `CONFIG_DRM_PANEL_HIMAX_HX8394=y` replaces `DRM_PANEL_SIMPLE`.
- **Decision on the sequence:** exact stock bytes (proven on this unit) rather than mainline's Waveshare sequence. They differ in the tail only: mainline sends `B1 00` and `BD 00` after `BD 01`; the stock table does not. If the screen stays dark, the first variant to try is mainline's tail.
- **Not explained by this:** TCON `CPU_IF` (+0x60, bit 22 vs the FIFO-flush bit 16), DCLK enable bits (+0x44), and the DSI trigger words (+0x160..+0x168, +0x1f0) differ. They are unlikely to matter in video mode but stay on the list if the init does not fix it.
- **Result (2026-11-08, image `a54da0ea…`, cards 3 and 4):** **the screen works.** The user booted card 3 and the console text is on the panel. So the cause of the black screen was the missing HX8394 initialisation (plus PE5 polarity); clocks, TCON, DSI timing and mode flags were already right. The exact stock byte sequence worked; mainline's tail variant (`B1 00`, `BD 00`) was not needed.
- **Open:** orientation/rotation (the panel is portrait; `fbcon=rotate:3` is on the command line, not yet judged), touch, backlight PWM (software PWM on PG10), USB host VBUS (PG12), Wi-Fi. The TCON/DSI differences listed above did not matter.

Result on the board: the I2C bus works (`Goodix-TS 0-0014` bound), but the probe fails with `Failed to get irq GPIO` (-22), and an `i2cdetect` of the bus shows **only 0x64** (an ATSHA204A). Nothing at 0x14 or 0x5d.
- **Why the node was wrong (all from the stock side):** the stock DTB marks both `twi@2502000` and its child `ctp@14` `status = "disabled"`; PB6/PB7 are the UART3 console pins (the stock pinmux shows `uart3` on both, and the register dump has them at mux 7); the working stock system has **no** touch-related GPIO or EINT configured at all (only PF6 as the SD card-detect EINT; PG12 is `usb1-vbus`, PG13/PG14 are `bt_wake`/`bt_hostwake`); and `allwinner,sun8i-ts` in the DTB is the thermal sensor. The stock kernel image has no touch driver strings and the rootfs has no touch module.
- **Working theory (Inferred, not yet confirmed):** the touch panel is a USB HID touch device on the T113's internal USB host port, which needs no I2C/INT/reset pins. The stock system drives PG12 (host VBUS) high; the mainline DTS never did (`usb1_vbus-supply` pointed at an always-on 5 V rail without the PG12 switch), so the port was unpowered and nothing could enumerate.
- **Also noticed:** `sdc1` (PG0-PG5) and `uart1` (PG6-PG9) plus `bt_wake`/`bt_hostwake` on the stock system mean there is an SDIO Wi-Fi/Bluetooth module on the board, in addition to the supplied USB RTL8188GU adapter. To check when doing Wi-Fi.
- **Changed (not yet run on the board):** `reg_usb1_vbus` regulator on PG12 (active high, always on) feeds `usb1_vbus-supply`; the Goodix node is removed (I2C2 stays, for the ATSHA); kernel gets `HID_MULTITOUCH`, `HIDRAW`, `TOUCHSCREEN_USB_COMPOSITE`; image gets `usbutils` (lsusb).
- **Test:** boot, `lsusb` / `/sys/bus/usb/devices`; if a touch HID device appears, `evtest` it. If nothing enumerates, the next candidates are an SPI/UART touch MCU (stock `uart1` is claimed, but by the Bluetooth lines) and reading `/proc/bus/input/devices` and `/proc/interrupts` on the stock system with the hook method of D-017.
- **Runtime GPIO write did not take:** setting PG12 as an output worked (`devmem` on the PIO config register) but the data bit would not latch (read back 0) in two tries; the kernel has no GPIO sysfs. Cause not found; the proper regulator in the DTS replaces the experiment.
- **Correction and result of the USB test (image `29ad4b67…`):** with PG12 powered the only device on the internal host port is the Wi-Fi dongle in CD-ROM mode (`0bda:1a2b`), so VBUS works (needed for Wi-Fi), but there is no touch device on USB and no input device at all. The USB-touch theory is refuted.
- **Found:** the stock DTB enables `rtp@2009c00` (`allwinner,sun8i-ts`): the SoC's **resistive touch-panel ADC**, with sensitivity 15 and filter type 1. This explains the missing pins and the stock userspace (tslib `pthres`/`variance`/`dejitter`/`linear`). My earlier remark that `sun8i-ts` is the thermal sensor was wrong; it is the touch ADC.
- **Changed (not yet run on the board):** new driver `patches/linux/0003` (`drivers/input/touchscreen/sun20i-d1-ts.c`, binding `allwinner,sun20i-d1-ts`, register programming from the vendor GPL driver), DTS node `touchscreen@2009c00` (IRQ SPI 62, `CLK_BUS_TPADC`/`CLK_TPADC`/`RST_BUS_TPADC`, sensitivity 15, filter 1), `CONFIG_TOUCHSCREEN_SUN20I_D1=y`. Image `150f8aa2…`.
- **Test:** `dmesg | grep sun20i`, `/proc/bus/input/devices`, then `evtest` on the new event device while touching the screen. Raw X/Y are 0..4095; mapping to the 720x1280 screen (and the rotation) is a calibration step for userspace or `touchscreen-*` DT properties.

## D-023 The key events come over UART1 at 115200; protocol decoded (2026-11-08)
- **Observed (mainline image `dbb79615…`, UART1 enabled):** this kernel names UART1 `ttyS0` (UART0 is disabled), so `/dev/ttyS1` does not exist; my first recorder listened to nothing. - **Meaning:** the SK-18 reports **keys**, not coordinates; no kernel touchscreen driver is needed. The same controller is the USB HID keyboard seen on the host (`4250:426f`; Inferred from the matching key codes). This closes the question from D-005 (`/dev/ttyS1` was the right guess).
- **Still open:** commands from the SoC to the controller (if any), other message types, and the stock host-port interrupt storm. UART1's DTS node stays; the key reader belongs in the on-device client.

## D-026 Wi-Fi in the image (2026-11-08)
- **Hardware facts used:** the supplied adapter is an RTL8188GU (RTL8710BU family). It first appears as a USB CD-ROM (`0bda:1a2b`, "Realtek DISK") and after the mode switch as `0bda:b711`; mainline's `rtl8xxxu` lists `0xb711` as tested, so no experimental option is needed; it loads `rtlwifi/rtl8710bufw_SMIC.bin` or `_UMC.bin`. The adapter sits on the internal USB host port, powered since the PG12 VBUS regulator (D-021/D-022 work).
- **Kernel:** the image had no wireless at all (`CONFIG_WIRELESS` off). Now `CFG80211`, `MAC80211`, `RTL8XXXU` (built in) with the Realtek WLAN vendor option and `RFKILL`.
- **Firmware:** own package `sk18-wifi-firmware` that downloads only the two blobs and the Realtek licence from the linux-firmware release Buildroot pins (`20261019`), hash-pinned (the full tarball is several hundred MB). The licence permits binary redistribution if the copyright and disclaimer are reproduced; the text is installed in `/usr/share/doc/sk18-wifi-firmware/`. The blobs are never committed.
- **Userspace:** eudev (hotplug, needed to trigger the mode switch), `usb_modeswitch` + data, `wireless-regdb`, `wpa_supplicant` with nl80211, `iw`. Predictable interface names are off (`net.ifnames=0`) so the adapter is `wlan0`. A udev rule runs `ifup wlan0` (through the helper `sk18-wlan-up`, so udev does not wait for DHCP) when the interface appears; `wlan0` is `inet dhcp` with `wpa-conf /etc/wpa_supplicant.conf`.

The eject action should be right for ours (Realtek reuses the ID), the target check will not match `0bda:b711`. Whether the shipped rule switches this adapter is untested; if not, an own rule with `usb_modeswitch -K -v 0bda -p 1a2b` is the fix.
- **Credentials:** not in the repo or the image. `tools/flash/provision-wifi.sh` (run by the user on the DietPi machine, card in the reader) asks for SSID, country and passphrase (no echo), stores the SSID as hex and the derived 256-bit key (PBKDF2, not the passphrase) in `/etc/wpa_supplicant.conf` on the card, mode 0600. ## D-028 Backlight: a real PWM driver for the T113 (2026-11-08)
- **Why:** the interim backlight was a software PWM (`pwm-gpio`, a 1 kHz hrtimer on the CPU) on PG10. It works, but its edges move with CPU load, and a smooth fade and a stable panel need the hardware block. Mainline 7.3.1 has no driver for it: `pwm-sun4i` knows only the A10, A13, H3 and H6 layouts, and the T113 dtsi has no PWM node.
- **Source of the register facts:** the stock DTB (`allwinner,sunxi-pwm`, 8 channels, block at `0x02000c00`, channel 3 on PG10 at 1 kHz), the stock register dump (PG10 in mux 2) and Allwinner's GPL vendor driver `pwm-sunxi-group.c`, "v200" layout: per-pair clock config at `0x20 + pair*4` (divider 2^DIV_M, bits 3:0; clock source bits 8:7), per-channel clock gate in `0x40`, per-channel enable in `0x80`, per-channel control at `0x100 + ch*0x20` (prescaler K bits 7:0, active-high bit 8) and period/duty at `+4` (entire-1 in bits 31:16, active in bits 15:0). Mainline's CCU already provides `CLK_BUS_PWM` and `RST_BUS_PWM`.
- **Driver:** `patches/linux/0003` adds `drivers/pwm/pwm-sun20i-d1.c` (compatible `allwinner,sun20i-d1-pwm`, state based `.apply`/`.get_state`, 8 channels, the 24 MHz oscillator as the counter clock, period and duty from nanoseconds with divider and prescaler chosen to fit 16 bits; a channel is refused with -EBUSY if its pair neighbour runs on a different divider), its devicetree binding, and the Kconfig/Makefile entries. Single-channel mode only (no pulse mode, dead zone, capture or groups). Compiled with the kernel's own flags before the full build.
- **DTS:** `pwm@2000c00` node in the board file (clocks `bus` and `hosc` = the 24 MHz `dcxo`), `pwm3_pg10_pins` (function `pwm3`), the backlight uses `<&pwm 3 1000000 0>`; the `pwm-gpio` provider and `CONFIG_PWM_GPIO` are gone.
- **Default brightness is still 128** so the image stays usable until the boot animation exists. For the animation the default becomes 0 (dark until userspace sets the level).
- **Image `37177392…`** flashed to the reader card. **Untested on the board:** that it probes, that the PWM registers hold the expected values (channel 3 period 24000 counter clocks at 24 MHz = 1 kHz), and that the brightness steps look right.

## D-029 Backlight verified on the board (2026-11-08)
- **Probe and registers (image `37177392…`):** the PWM controller registers as `platform/2000c00.pwm`, `npwm: 8`; channel 3 is owned by the backlight, requested 501960/1000000 ns, actual 501959/1000000 ns, normal polarity. Registers: `PCGR` 0x8 and `PER` 0x8 (channel 3 clocked and enabled), pair clock `PCCR` 0 (24 MHz oscillator, no divider), `PCR3` 0x100 (active high, prescaler 0), `PPR3` entire = 0x5DBF (24000 clocks = 1 kHz exactly).

- **Flasher change:** `tools/flash/flash-sdcard.sh` now carries a card's Wi-Fi credentials over to the new image when the card being flashed already has a `network=` block in `/etc/wpa_supplicant.conf` (temporary 0600 file on the DietPi machine, removed on exit; the file is installed 0600 after the read-back check, so the card then differs from the image by that one file). A card without credentials needs `provision-wifi.sh` once.

## D-032 The first animation test failed: no /dev/fb0 (2026-11-08)
- **Observed (image `9a789989…`):** the user saw an all black screen. The kernel log on the board said `sk18-splash failed: switching the backlight on` at 8.4 s, i.e. the animation program gave up after waiting its 5 s for the framebuffer, and the init script's safety net switched the backlight on. The kernel itself had registered a framebuffer (`fb0: sun4i-drmdrmfb frame buffer device`, 2.7 s) but `/dev/fb*` did not exist and `/sys/class/graphics` held only `fbcon`.
- **Cause:** `CONFIG_FB_DEVICE` was off. It controls the legacy `/dev/fb*` node and its sysfs entries; it defaults to `FB`, which is also off here (only `FB_CORE` and the DRM fbdev emulation are on). The text console does not need it, which is why every earlier screen test worked.
- **Fix:** `CONFIG_FB_DEVICE=y` in the kernel fragment. Also: `S00splash` now puts the program's own error text into the kernel log (it went to `/dev/null` before), so the next failure explains itself on the serial link.
- **What held up:** the "no boot text" part (the user saw none) and the fail-safe (the backlight came on although the animation did not run).
- **Lesson:** I assumed `/dev/fb0` exists on the strength of the display working and did not check the device node before building on it. Checking the interface a program depends on, on the real image, comes before building the program.
- **Image `7a2eb325…`** flashed with the credentials carried over. The animation itself (colours, letters, timing, orientation) is still unverified on the board.

### D-037 update — cause and fix of the receive stalls (2026-11-09)

- Evidence: during a stall the daemon was alive (polling every 30 ms), the board's USB controller kept taking about 64 interrupts a second (matching the host's 58 KB frames every 1.6 s), the host's usbmon showed every OUT transfer accepted, and yet no frame reached the daemon. Earlier runs showed replies arriving one request late and `getInfo` answers appearing only when a later large transfer arrived. A single ACM function (console removed) stalled just the same.
- Conclusion: the terminal (n_tty) holds the data but the reader is not woken: a lost wakeup in the kernel's line discipline on this dual-core CPU. My first watchdog (`tcflush` on every idle poll) made it worse, because the flush discarded the very data the reader had not been woken for.
- Fix: after a 20 ms poll timeout the daemon asks the terminal how many bytes it holds (`FIONREAD`) and reads them; only when the terminal is empty does it `tcflush(TCIFLUSH)` (which also ends in `tty_unthrottle()`, covering a throttled gadget). No data is discarded.
- Status: to be verified on the board with the gateway running.

### D-037 correction — it was my flush (2026-11-09)

- The read-loop statistics added to the verbose log showed the real cause of the "stalls": the daemon was reading every frame in full (`reads`/`bytes` growing, one 58 KB frame every ~2 s) but the decoder dropped almost every one (`dropped` +1 per frame, `buffered` ~58 KB): each frame failed its data CRC. `flushes` equalled `timeouts`: the idle `tcflush(TCIFLUSH)` ran continuously and cut holes into frames still arriving. The "lost wakeup" and "throttled gadget" theories had no support in that data, and a second reader on the same port received intact frames.
- Fix: no flush at all. After a poll timeout the daemon only reads data the terminal already holds (`FIONREAD`), which is harmless. The frame size limit is 2 MiB.
- Lesson: the one-late replies of the first image (no flush) may have a different cause (they were seen with the same `read` loop, blocking); to be re-checked with the statistics before assuming that part is fixed.

### D-037 update 2 — packets are lost on the receive path (2026-11-09)

- Evidence that overturns the "decoder/CRC" and "flush" explanations: the daemon saved a bad frame; compared byte for byte with what Python had sent, the received stream was correct up to offset 17408 (34 packets) and shifted by +512 bytes after it (and +1024 later): whole 512-byte USB packets vanish between the controller and the daemon. The constant trailer value in every gateway frame is the same effect: the decoder's "trailer" falls into the start of the next frame's identical JPEG header. A plain `cat` reader (no daemon) got only 1,212,392 of 2,097,152 bytes of a 2 MB flood. The interrupt count matches the packet rate (every packet reaches the controller driver). A packet with `RXPKTRDY` set and no request waiting was seen in the controller registers during a stall.
- Causes ruled out: Wi-Fi (dongle detached, still bad), display scan-out (blanked, still bad), a second daemon (found once, only after my own restart), CPU frequency (no cpufreq), packet size or timing from the host (identical URB pattern from Python and gateway), forcing full speed (`sunxi-musb does not have testmode`; configfs `max_speed` below high-speed is refused by `musb_gadget_start`).
- Hypothesis being tested: u_serial queues only 16 one-packet requests; a 58 KB frame is ~114 back-to-back packets, so the queue runs dry in every burst and the controller driver's "no request, interrupt consumed" path loses or strands packets. Kernel patch 0004 raises `QUEUE_SIZE` to 256.
- Note for the init script: `S90sk18-link stop` does not stop a running daemon (a restart started a second one, and two readers split the data). Fix before shipping.

## D-041 — SK-18 deck protocol over USB HID (2026-11-10)

- **Decision (user):** "do SK-18 over HID". The SK-18 appeared to the gateway as `serial /dev/ttyACM0` while the Stream Deck is `hid /dev/hidraw4`; the user asked whether the SK-18 could be HID too.
- **Built:** the gadget has a HID function (`hid.usb0`, `/dev/hidg0`, 512-byte vendor reports, no report ids, interval 1) and one CDC-ACM console (`ttyGS0`, getty moved from `ttyGS1`); the deck protocol is carried unchanged as a byte stream cut into 512-byte reports `[len u16][<=510 bytes]`. Kernel: `CONFIG_USB_CONFIGFS_F_HID=y` and patch 0005 (`f_hid` receive queue 4 -> 1024, same reason as patch 0004). `sk18-link` has a `HidPort` (selected when `--port` is a `hidg*` node, default `/dev/hidg0`); `deck-sk18` lists `hidraw` nodes, opens them, and prefers a HID node over the serial ports of the same USB device. Serial stays supported on both sides (stock firmware, older images). Details: `docs/hid-transport.md`.
- **Why 512 and interval 1:** the sunxi musb FIFOs are 512 bytes and the `f_hid` default interval 4 allows one packet per millisecond (about 512 KB/s, 115 ms for a 58 KB picture).
- **Host:** udev rule for the hidraw node (manufacturer `SK18 open firmware`) added to `70-control-deck-sk18.rules`; gateway v8 deployed on the DietPi (device id unchanged: `waveshare-sk18`, no serial number).
- **Tests:** framing round trip and bad lengths on both sides; discovery prefers HID over serial. **Observed on the real board (image `4b4b91d6`, card flashed as a new card, Wi-Fi carried over):** the gateway lists it as `hid /dev/hidraw5` next to the Stream Deck's `hid /dev/hidraw4`, state attached, 18 keys, no warnings; the user confirmed that images show and keys respond. Throughput and unplug/replug recovery not measured separately.
- **Still open:** the ~5 pictures per second seen in the old log before the 2026-11-10 stop (what repaints that often?).
